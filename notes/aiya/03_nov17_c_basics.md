# Контекст

Прошлая лекция закончилась схемой простейшего компьютера (рис. [-@fig:lec02:computer]): процессор с регистрами и АЛУ, адресуемая память, где лежат и программа, и данные, шина и внешние устройства. Машина Тьюринга нужна была, чтобы понять, что вычислимо в принципе, а писать программы курс будет для этой схемы и на языке C. Эта лекция начинает язык: откуда он взялся и почему стандарт устроен так, как устроен; что делает каждая строка первой программы; какая бывает память у переменных; какие в C базовые типы, что стандарт о них гарантирует и что оставляет на выбор; как целые числа лежат в памяти байтами.

# Теория

## Язык C и его стандарты

C разрабатывался для реализации UNIX, первой универсальной операционной системы. До этого каждая фирма выпускала компьютеры со своим набором команд, и системные программы для каждой машины писали на её языке ассемблера. Операционная система, одна для разных компьютеров, требует языка, который не привязан к конкретному процессору, но позволяет делать всё, что нужно системной программе: работать с памятью, с устройствами, управлять задачами. Таким языком и стал C.

Порядок событий был обратным тому, что кажется естественным. Сначала появился язык и компилятор, и правильной программой на C считалось то, что компилятор принимал. Когда компиляторов для разных машин стало много, понадобилось общее описание языка, иначе программа, написанная для одной машины, не собиралась бы на другой. Им стала книга авторов языка, а за ней пошли стандарты.

| Год | Событие |
| --- | --- |
| 1973 | первая версия C |
| 1978 | книга Б. Кернигана и Д. Ритчи «Язык программирования Си» (K&R C); русский перевод — 1985 |
| 1989 | первый стандарт ANSI C (C89) |
| 1999 | стандарт C99 |
| 2011 | стандарт C11: `_Thread_local`, `_Generic`, `_Alignas`, `_Noreturn` и другое |
| 2018 | стандарт C18 (его называют и C17): только исправления ошибок C11 |
| 2024 | стандарт C23 (ISO/IEC 9899:2024): много изменений |

Языки развиваются двумя способами. У C и C++ есть *комитет по стандартизации* (у C — рабочая группа ISO WG14): в нём сидят компании, которые делают компиляторы и системы на C (IBM, Red Hat, Oracle, Microsoft и другие), у каждой свои интересы, и стандарт — результат их договоренности. Плюс в том, что ни одна платформа не окажется за бортом: её владелец участвовал в обсуждении. Минус в том, что договориться трудно, а если включать в язык пожелания всех, язык разрастается и теряет цельность. У Java, Python и C# другой путь: язык развивает один владелец (компания или автор), и языком считается то, что он назовет языком. Так язык получается последовательнее, но если владелец идет не туда, поправить его некому. Чтобы назвать свою виртуальную машину Java, нужно пройти тесты на соответствие спецификации владельца (conformance testing). У Python тоже нет стандарта ISO: язык описывают документация и предложения по развитию (PEP).

Цена договоренностей видна на C23. Летом 2024 года, пока в комитете шли правки, истек срок публикации, и ISO автоматически отменило проект стандарта ISO/IEC 9899:2023. Стандарт вышел позже в том же году как ISO/IEC 9899:2024, но название C23 за ним осталось.

::: {.remark #rem:lec03:c99 tag="соглашение курса"}
Основа курса — C99: на нём пишутся программы курса. Где C11 и C23 что-то меняют, это оговаривается отдельно. Код в конспектах проверен компилятором GCC в режимах `-std=c17` и `-std=c23` (в GCC 13 — `-std=c2x`) с флагами `-Wall -Wextra`; если результат зависит от стандарта, это сказано рядом.
:::

### Почему C

C живет около 50 лет. Языки вроде Rust нацелены на ту же нишу системного программирования и закрывают его слабые места, прежде всего с безопасностью работы с памятью, но настолько распространенными пока не стали. На C написаны ядра Linux и Windows, базы данных PostgreSQL и SQLite, интерпретатор Python (CPython), криптографическая библиотека OpenSSL. Свойства, которые сделали C популярным:

- *императивный язык*: программа говорит, что делать шаг за шагом, как алгоритм из первой лекции. Так ближе к тому, как человек обычно думает о процессе. Функциональные языки, где программа — набор функций в духе математики, хорошо развивают алгоритмическое мышление, и некоторые университеты начинают обучение с них; спор, какой подход лучше, давний и без победителя;
- *удобный синтаксис*: фигурные скобки, циклы `for` и `while` перешли из C во многие языки;
- *естественно работать с «машинными» понятиями*: язык не прячет от программиста ни память, ни адреса, ни представление чисел. Всё, что умеет процессор, можно использовать, но и ответственность за ошибки целиком на программисте: в языках для массовой прикладной разработки от таких ошибок часто ставят защиту, в C её нет;
- *переносимость на уровне исходного кода*: программу, написанную на x86, можно собрать компилятором другой машины, например мейнфрейма IBM, и получить машинный код для её процессора. Большая программа обычно еще и *конфигурируется* под платформу: размеры типов, наличие библиотек;
- *хорошие системные библиотеки*: ввод-вывод, математика, работа со строками и памятью;
- *хорошие оптимизирующие компиляторы*: GCC, Clang, компиляторы Intel и IBM; многие приемы оптимизации сначала отрабатывались на C.

::: {.remark #rem:lec03:binary-portability}
Переносимость исходного кода не то же самое, что переносимость готовой программы. Скомпилированная программа на C — машинный код одного процессора, на другом она не запустится. Java обещает «написал один раз — запускай везде» для уже собранной программы: компилятор выдает не машинный код, а байт-код виртуальной машины, а на каждой платформе своя виртуальная машина исполняет его или дособирает в родной машинный код.
:::

## Первая программа

Самая известная программа на C пришла из книги Кернигана и Ритчи:

```c
#include <stdio.h>

int main(void)
{
    printf("Hello, world\n");
    return 0;
}
```

Она печатает `Hello, world` и переводит строку. В пяти строках видны почти все главные идеи языка: функции, объявления, препроцессор, строковые константы и форматный вывод, код завершения.

### Функции, объявления и определения

Данные программы лежат в памяти. Чтобы не работать с голыми адресами, участку памяти дают имя: это *переменная*. Код делится на *функции*: кусок кода с именем, который можно вызывать из разных мест. Это тот же прием, что в диаграммах Тьюринга, где готовая машина используется как часть другой (пример [-@ex:lec02:copy]). Выполнение начинается с функции `main` — у программы должна быть точка входа, как начальное состояние $q_0$ у машины Тьюринга.

Тела функции `printf` в программе нет: её написали авторы стандартной библиотеки, а программа её только вызывает. Чтобы скомпилировать вызов, компилятору не нужно тело. Ему нужно знать, как функция называется, сколько у неё параметров, какого они типа и что она возвращает. Тогда `main` сможет положить аргументы туда, откуда `printf` их заберет: функции написаны независимо, и работать вместе они могут только по общему соглашению о передаче параметров. Как устроено это соглашение, будет видно, когда дойдем до автоматической памяти и вызова функций.

::: {.definition #def:lec03:declaration title="объявление и определение функции"}
*Объявление* функции (заголовок, прототип) сообщает компилятору её имя, число и типы параметров и тип результата. *Определение* функции — объявление вместе с телом: кодом, который выполняется при вызове. Программа на C состоит из объявлений переменных и функций и определений функций.
:::

У `main` в программе выше есть определение: заголовок `int main(void)` (функция без параметров, `void` — «ничего», возвращает целое `int`) и тело в фигурных скобках. У `printf` в программе нет ничего, её объявление приходит из файла `stdio.h`. В библиотеке GCC оно выглядит так (служебные слова убраны):

```c
int printf(const char *format, ...);
```

Имя `printf`, результат типа `int`, первый параметр — форматная строка, многоточие означает «дальше сколько угодно аргументов». Что такое `const char *`, разберем вместе с указателями и строками.

::: {.remark #rem:lec03:declaration-needed tag="подводный камень"}
Если убрать `#include <stdio.h>`, объявления `printf` не будет. По стандарту C99 вызов необъявленной функции — ошибка, компилятор обязан выдать диагностику. GCC 13 печатает предупреждение `implicit declaration of function 'printf'` и всё же собирает программу: старый C разрешал вызывать необъявленные функции, считая, что они возвращают `int`. GCC 14 и новее выдают ошибку. Предупреждение о неявном объявлении — признак ошибки в программе, а не мелочь: компилятор не знает типов параметров и не может проверить вызов.
:::

### Препроцессор

Объявления библиотечных функций лежат в *заголовочных файлах*, и их нужно вставить в программу. В Java или Python компилятор сам читает описание подключенного модуля или пакета; в C эту задачу решает отдельный этап до компиляции — *препроцессор*. Его команды (*директивы*) начинаются с символа `#`. Директива `#include <stdio.h>` заменяется содержимым файла `stdio.h` из системного каталога заголовков, и компилятор получает текст, где объявление `printf` уже есть.

Препроцессор работает с текстом и не вникает в его смысл: он заменяет одни куски текста другими, будь то объявления функций или скобки. После препроцессора пятистрочная программа превращается примерно в 820 строк (команда `gcc -E hello.c` показывает этот текст); почти все они — объявления из `stdio.h`, среди них и строка с `printf`. Другие директивы препроцессора разберем ближе к концу курса.

### Строковые константы и форматный вывод

`"Hello, world\n"` — *строковая константа*: текст в двойных кавычках. Программа общается с внешним миром через *стандартный поток ввода* (обычно клавиатура) и *стандартный поток вывода* (обычно экран). В C от UNIX пришла идея, что программы удобнее всего связывать текстом: вывод одной подается на вход другой. Поэтому вывод в C — это текст. Систему вывода можно устроить по-разному: отдельная функция для каждого типа (неудобно), одна функция, перегруженная для разных типов (в C перегрузки нет), отдельные функции, которые печатают и которые управляют выводом (как `write` и `writeln` в Паскале). В C печатью и управлением выводом занимается одна функция семейства форматного вывода, `printf`. Что печатать и как, она узнаёт из одного параметра.

::: {.definition #def:lec03:format-string title="форматная строка"}
*Форматная строка* — первый аргумент `printf`. Обычные символы в ней печатаются как есть. *Управляющая последовательность* начинается с обратного слэша и обозначает символ, который иначе не записать: `\n` — перевод строки, `\t` — табуляция, `\"` — кавычка, `\\` — сам обратный слэш. *Спецификатор формата* начинается с `%` и говорит, куда и как подставить значение следующего аргумента: `%d` — целое число типа `int`, `%%` — сам знак процента.
:::

Раз управляющий текст и печатаемый текст записаны вперемешку, их нужно различать, отсюда спецсимволы `\` и `%`. А раз они спецсимволы, вывести их самих можно только удвоением.

::: {.example #ex:lec03:printf title="форматная строка с подстановкой"}
```c
#include <stdio.h>

int main(void)
{
    printf("%d + %d = %d\n", 2, 3, 2 + 3);
    printf("Файл лежит в C:\\temp\\notes\n");
    printf("Он сказал: \"привет\"\n");
    return 0;
}
```

Первый `%d` получает $2$, второй $3$, третий значение выражения `2 + 3`. Программа печатает:

```
2 + 3 = 5
Файл лежит в C:\temp\notes
Он сказал: "привет"
```
:::

Других спецификаторов много (`%u`, `%ld`, `%c`, `%s` и т. д.), их будем вводить вместе с типами, для которых они нужны. Когда подставлять нечего, хватает функций попроще из того же `stdio.h`: `puts("Hello, world")` печатает строку и сама добавляет перевод строки, `putchar('A')` печатает один символ.

### Код завершения

`return 0;` завершает `main` и возвращает число $0$. Оно нужно не программе, а операционной системе. Система запускает программы, часто цепочкой одну за другой, и должна узнать, успешно ли программа закончилась. Единый способ — *код завершения*: целое число, которое возвращает `main`. Соглашение такое: $0$ — успех, не $0$ — ошибка. В командной строке Linux код последней программы показывает `echo $?`: если в программе написать `return 3;`, после её запуска `echo $?` напечатает `3`.

::: {.remark #rem:lec03:main-return tag="корнер-кейс"}
Если выполнение дошло до закрывающей скобки `main` без `return`, программа всё равно возвращает $0$: так требует стандарт начиная с C99. Для других функций, возвращающих значение, этого правила нет. Писать `return 0;` в `main` всё же принято: так видно, что программа завершилась успешно намеренно.
:::

### Сборка и запуск

Программу на C перед запуском *компилируют*: компилятор переводит исходный текст `hello.c` в машинный код процессора и записывает его в исполняемый файл, а операционная система загружает этот файл в память и запускает. С Python иначе: программу `hello.py` при каждом запуске читает и выполняет интерпретатор `python3`. В Linux сборка и запуск выглядят так:

```
$ gcc -Wall -Wextra -Werror hello.c -o hello
$ ./hello
Hello, world
```

Флаг `-o hello` задает имя исполняемого файла. Остальные флаги управляют сообщениями компилятора, а сообщения бывают двух видов. *Ошибка* (error) означает, что текст не соответствует языку; исполняемый файл тогда не создается. *Предупреждение* (warning) компилятор выдает, когда программа собирается, но в ней есть подозрительное место (например, неиспользуемая переменная или всегда истинное сравнение) либо нарушение правил типов/объявлений, которое старые компиляторы для совместимости всё еще пропускают. Без флагов GCC выдает только часть предупреждений, `-Wall` и `-Wextra` включают большинство полезных, а `-Werror` превращает каждое предупреждение в ошибку.

::: {.example #ex:lec03:warning title="предупреждение и -Werror"}
В «Hello, world» вместо `return 0;` написали `return "I am a warning!";`. Функция `main` обещает вернуть `int`, а возвращает строку — это нарушение правил типов стандарта C. Clang и GCC 14 сразу выдают ошибку, а GCC 13 для совместимости программу собирает, но предупреждает:

```
warning: returning 'char *' from a function with return type 'int'
makes integer from pointer without a cast [-Wint-conversion]
```

С флагом `-Werror` то же сообщение у GCC 13 начинается словом `error`, а в скобках стоит `-Werror=int-conversion`; исполняемого файла нет. Предупреждение о неявном объявлении `printf` из замечания [-@rem:lec03:declaration-needed] — из того же ряда: на части компиляторов программа собирается, но в ней ошибка.
:::

Дальше примеры курса собираются с `-Wall -Wextra`. Многие ловушки C, о которых пойдет речь, компилятор с этими флагами замечает сам, если читать его предупреждения.

## Классы памяти

Изучение любого языка начинается с *типов*: что можно хранить в памяти и что с этим можно делать. Потом изучают, как программа обрабатывает значения этих типов. Но прежде чем говорить о типах, нужно уточнить, как устроена память.

::: {.definition #def:lec03:byte title="байт"}
*Байт* — наименьший участок памяти, у которого есть свой адрес. Соседние адреса — соседние байты. Размеры всех типов в C измеряются целым числом байтов.
:::

Обычно байт — это $8$ бит, но так бывает не всегда: если память машины адресуется только кусками по $16$ бит, байт на ней $16$-битный. Стандарт C требует лишь, чтобы бит в байте было не меньше $8$ (их число — константа `CHAR_BIT` из `limits.h`).

### Зачем нужны классы памяти

На схеме компьютера (рис. [-@fig:lec02:computer]) про память было сказано одно: в ней по адресам лежат программа и данные. Для языка этого мало. Если посмотреть, когда и зачем программе нужны её переменные, видно, что они бывают разные:

- переменные, через которые функции обмениваются данными, должны жить всё время работы программы: до запуска неизвестно, какие функции и в каком порядке будут вызваны;
- промежуточные значения внутри функции нужны, пока функция работает. Функция, вычисляющая $\sin x$ суммой ряда, хранит частичные суммы, а тому, кто вызвал её, нужен только результат;
- бывают данные, сколько их будет, становится известно только при работе программы: например, программа читает с клавиатуры числа, пока не встретит ноль.

::: {.definition #def:lec03:storage-class title="классы памяти"}
*Класс памяти* переменной определяет, где она хранится и когда память под неё выделяется и освобождается.

- *Статическая* память нужна всё время работы программы: глобальные переменные (объявленные вне всех функций) и сам текст программы. Её объем известен до запуска, она выделяется до начала `main` и живет до конца программы.
- *Автоматическая* память нужна на время работы функции: локальные переменные. Её выделяет и освобождает код, который компилятор сам вставляет в начало и в конец функции.
- *Регистровая* память — регистры процессора, самая быстрая память. Программист на C регистрами не управляет, он может только подсказать компилятору, что переменную стоит держать в регистре (слово `register`).
- *Динамическая* память выделяется и освобождается по явной команде программы: когда при компиляции неизвестен объем данных или момент, когда они перестанут быть нужны.
:::

### Кто управляет памятью

Почему автоматическую память можно отдать компилятору, а динамическую нельзя? Чтобы управлять памятью без участия программиста, нужно еще до запуска знать две вещи: сколько памяти нужно и когда она рождается и умирает. Для статической памяти известно и то и другое: объем всех глобальных переменных считается по тексту программы, а живут они всю работу программы. Для автоматической тоже: компилятор видит, какие локальные переменные есть у функции, а живут они от входа в функцию до выхода из неё. Заставлять программиста вручную выделять память под локальные переменные каждой функции значило бы мучить его без нужды. Динамическая память — ровно то, где одно из двух неизвестно: либо объем (сколько чисел введет пользователь), либо время жизни (память выделили в одной функции, а освободить её могут в разных местах программы). Тогда управлять ею должен программист. В C он сам и выделяет, и освобождает её. Во многих других языках программист только выделяет память, а ненужную находит и освобождает *сборщик мусора*. Динамическую память разберем отдельно позже.

::: {.example #ex:lec03:storage-classes title="классы памяти в одной программе"}
```c
#include <stdio.h>

int calls = 0;              /* статическая память */

int square(int x)
{
    int result = x * x;     /* автоматическая память */
    calls = calls + 1;
    return result;
}

int main(void)
{
    register int s = 0;     /* подсказка: держать в регистре */
    s = square(3) + square(4);
    printf("s = %d, calls = %d\n", s, calls);
    return 0;
}
```

Глобальная `calls` создается до `main` и помнит, сколько раз вызывали `square`. Локальная `result` создается при каждом входе в `square` и пропадает при выходе. Программа печатает `s = 25, calls = 2`.
:::

::: {.remark #rem:lec03:register-hint}
`register` — только подсказка. Компилятор может её не выполнить, а может, наоборот, сам держать в регистре переменную без этого слова: современные компиляторы распределяют регистры лучше программиста. Поэтому в новом коде `register` почти не пишут.
:::

## Базовые типы

Типы, которые язык дает «из коробки», определяются тем, что умеет процессор: команды для целых чисел, для отдельных битов и для вещественных чисел. Строк процессор обычно не знает, но многие языки добавляют их как встроенный тип, потому что после чисел строки нужнее всего. В C строки встроенным типом не стали.

Базовые типы C: `char` (символьный), `int` (целый), `float` (с плавающей точкой), `double` (с плавающей точкой двойной точности) и комплексный модификатор `_Complex` (с C99; пишется вместе с вещественным типом: `float _Complex`, `double _Complex`, `long double _Complex`). Отдельно стоит тип `void` — «без значения». Модификаторы базовых типов: `signed`, `unsigned`, `short`, `long`, `long long` (с C99). К `int` применимы все модификаторы, к `char` — только `signed` и `unsigned`, к `double` — только `long`.

### Символы — это числа

Отдельный символьный тип в C свели к целому. Это кодирование (утверждение [-@prop:lec01:encoding]): символы алфавита нумеруются, и в памяти хранится не символ, а его номер в выбранной кодировке. Значит, `char` — целое число, а символом оно становится, когда мы решаем прочитать его через таблицу кодировки.

### Целые типы: размер и знак

У целого типа фиксированный размер (число байтов) и *знаковость*: знаковый тип хранит отрицательные и положительные числа, беззнаковый — только неотрицательные. Сколько байтов отвести под `int`?

Слишком мало плохо: одного байта хватает на $256$ значений, этого мало почти для всего. Слишком много тоже плохо: под каждое число уходит лишняя память, а большинство чисел в программах невелики. Но главное в другом. Процессор складывает числа в АЛУ, и по каждому биту операнда идет свой проводник: чтобы сложить два $16$-битных числа за одну команду, нужно $16 + 16$ входов, для $32$-битных — $64$. Числа длиннее процессор складывает по кусочкам, несколькими командами. Поэтому для $16$-битного процессора естественный размер целого — $2$ байта, для $32$-битного — $4$. Если язык зафиксирует $4$ байта, на $16$-битной машине каждое сложение станет медленным, а через несколько лет придут $64$-битные машины, и $4$ байта будут неудобны уже им. C должен эффективно работать на разных процессорах, поэтому стандарт не фиксирует размеры, а дает *минимальные гарантии*. Размер типа не нужно путать с размером адреса: сколько байтов занимает число и сколько байтов нужно, чтобы указать на ячейку памяти, — разные вопросы (адресам посвящена тема указателей).

::: {.definition #def:lec03:int-types title="целые типы"}
Знаковые целые типы C — `signed char`, `short`, `int`, `long`, `long long`; у каждого есть беззнаковая пара с `unsigned`. Стандарт гарантирует:

- `char` занимает ровно $1$ байт: `sizeof(char) == 1`;
- `short` и `int` — не меньше $16$ бит, `long` — не меньше $32$, `long long` — не меньше $64$; при $8$-битном байте это $2$, $2$, $4$ и $8$ байтов;
- каждый следующий тип ряда `char`, `short`, `int`, `long`, `long long` вмещает все значения предыдущего, поэтому на практике
$$\mathtt{sizeof(char)} \le \mathtt{sizeof(short)} \le \mathtt{sizeof(int)} \le \mathtt{sizeof(long)} \le \mathtt{sizeof(long\ long)}.$$

Здесь `sizeof(T)` — размер типа `T` в байтах; так же `sizeof` работает с переменной: `sizeof(x)` для `int x` равен `sizeof(int)`. Точные границы значений каждого типа на данной машине — константы в `limits.h`: `INT_MIN`, `INT_MAX`, `CHAR_MIN` и т. д.
:::

Гарантия снизу нужна, чтобы тип был полезен: `long`, не вмещающий $32$-битных чисел, был бы не нужен. Порядок нужен, чтобы «длинный» тип не оказался короче «короткого». Всё остальное выбирает реализация. Самый частый набор сейчас: `char` — $1$ байт, `short` — $2$, `int` — $4$, `long` — $4$ (Windows) или $8$ (Linux и macOS на $64$-битных процессорах), `long long` — $8$. На старых $16$-битных машинах `short` и `int` были по $2$ байта, `long` — $4$. Стандарт допускает и машину, где `short`, `int` и `long` все по $4$ байта: так бывает, если процессор работает только с $4$-байтными регистрами и брать из них кусочки неудобно.

::: {.example #ex:lec03:sizes title="размеры типов на своей машине"}
```c
#include <limits.h>
#include <stdio.h>

int main(void)
{
    printf("char %zu, short %zu, int %zu, long %zu, long long %zu\n",
           sizeof(char), sizeof(short), sizeof(int), sizeof(long),
           sizeof(long long));
    printf("CHAR_BIT = %d, CHAR_MIN = %d, CHAR_MAX = %d\n",
           CHAR_BIT, CHAR_MIN, CHAR_MAX);
    return 0;
}
```

Спецификатор `%zu` печатает значение `sizeof`. На $64$-битном Linux с процессором x86-64 программа печатает

```
char 1, short 2, int 4, long 8, long long 8
CHAR_BIT = 8, CHAR_MIN = -128, CHAR_MAX = 127
```
:::

::: {.remark #rem:lec03:int-four tag="частое заблуждение"}
«*`int` — это 4 байта*». Так на большинстве современных компьютеров, но стандарт гарантирует только $16$ бит. Программа, которая полагается на $4$ байта (например, хранит в `int` числа до двух миллиардов), на машине с $2$-байтным `int` молча посчитает неправильно. Когда нужен точный размер, берут типы фиксированной ширины (ниже).
:::

::: {.remark #rem:lec03:byte-not-8 tag="корнер-кейс"}
Если байт на машине $16$-битный, `char` всё равно занимает $1$ байт, только этот байт из $16$ бит. Тогда и `int` может занимать $1$ байт: $16$ бит ему хватает. Поэтому гарантии стандарта сформулированы в битах, а «не меньше $2$ байтов» верно только при $8$-битном байте.
:::

Иногда нужен именно заданный размер, а не «самый удобный процессору»: например, в сетевом протоколе поля пакета имеют строго определенную длину. Для этого заголовок `stdint.h` (его же подключает `inttypes.h`) задает целые типы фиксированной ширины: `int8_t`, `int16_t`, `int32_t`, `int64_t` и беззнаковые `uint8_t`, …, `uint64_t` (буква `u` — unsigned).

### Умолчания

C позволяет писать коротко, если по короткой записи всё понятно; для этого нужны умолчания:

- целый тип по умолчанию знаковый: `int` значит `signed int`. Знаковая арифметика нужна чаще беззнаковой;
- `short` бывает только у целых, поэтому `short` значит `signed short int`; `long` без указания типа тоже означает целое `signed long int` (для вещественного пишут `long double` полностью);
- `unsigned` без типа значит `unsigned int`.

Вещественные типы — `float`, `double`, `long double`. Беззнаковых вещественных нет: знак хранится внутри представления числа, и отказ от него ничего не дает. Обычно `float` занимает $32$ бита, `double` — $64$, а `long double` на разных платформах устроен по-разному: $64$, $80$ или $128$ бит (на x86-64 Linux это $80$-битное число, под которое отводится $16$ байтов). Вещественные числа разберем отдельно.

### Знаковость `char`

С `char` умолчания нет. За беззнаковый `char` говорит то, что это символ, а у кода символа знака нет. За знаковый — то, что `char` самый маленький целый тип, и в нём удобно хранить небольшие числа, например от $-100$ до $100$; да и все остальные целые типы по умолчанию знаковые. Аргументы есть у обеих сторон, а компилятор поддерживает любой выбор одним флагом (ниже). Поэтому стандарт оставляет выбор реализации: `char` знаковый или беззнаковый в зависимости от платформы, а `signed char` и `unsigned char` — отдельные типы с известной знаковостью. GCC на x86-64 делает `char` знаковым (`CHAR_MIN = -128` в примере [-@ex:lec03:sizes]), на ARM под Linux — беззнаковым; флаг `-funsigned-char` меняет выбор, и тогда та же программа печатает `CHAR_MIN = 0, CHAR_MAX = 255`.

::: {.remark #rem:lec03:char-sign tag="частое заблуждение"}
«*`char` хранит символы, значит, он беззнаковый*». Знаковость простого `char` выбирает реализация. Если программа сравнивает `char` с числом больше $127$ или с отрицательным, её результат зависит от платформы. Когда важен знак, пишут `signed char` или `unsigned char` явно.
:::

## Что стандарт определяет, а что нет

Знаковость `char` — пример того, что стандарт сознательно не фиксирует. Стандарт C делит поведение программ на категории, и они понадобятся весь курс.

::: {.definition #def:lec03:behavior title="категории поведения"}
- *Определенное поведение*: стандарт однозначно задает результат. Пример: `sizeof(char) == 1`.
- *Поведение, определяемое реализацией* (implementation-defined): стандарт дает выбор, реализация (компилятор вместе с платформой) обязана выбрать и описать выбор в документации. Примеры: размер `int`, знаковость `char`.
- *Неуточненное поведение* (unspecified): стандарт допускает несколько вариантов, реализация выбирает любой и не обязана ни документировать выбор, ни делать его одинаково каждый раз. Пример: порядок, в котором вычисляются аргументы при вызове функции.
- *Неопределенное поведение* (undefined behavior, UB): стандарт не предъявляет к результату никаких требований. Программа с таким действием неправильная. Примеры: переполнение знакового целого, деление на ноль, выход за границы массива.
:::

Зависящее от реализации и неуточненное поведение — свобода, которая ничего не стоит: программа, написанная аккуратно, работает при любом выборе, а каждая платформа выбирает то, что ей удобнее. Это есть в любом языке. С неопределенным поведением иначе: компилятор вправе считать, что в правильной программе его не бывает, и строить на этом оптимизации.

::: {.example #ex:lec03:unspecified title="порядок вычисления аргументов"}
```c
#include <stdio.h>

int f(void)
{
    printf("f ");
    return 1;
}

int g(void)
{
    printf("g ");
    return 2;
}

int main(void)
{
    printf("%d %d\n", f(), g());
    return 0;
}
```

Последним всегда печатается `1 2`: сначала вычисляются оба аргумента, потом вызывается внешний `printf`. А кто из `f` и `g` напечатает свое раньше, стандарт не говорит. Программа, собранная GCC, печатает `g f 1 2`, собранная Clang — `f g 1 2`. Обе правильные. Так же не уточнен порядок вычисления операндов в `f() + g()`: сумма всегда $3$, а кто из функций вызовется первой, неизвестно.
:::

::: {.remark #rem:lec03:ub-optimization tag="подводный камень"}
«Программа отработала и выдала разумный ответ, значит, в ней нет ошибки» — для неопределенного поведения это не так. Функция

```c
int bigger(int x)
{
    return x + 1 > x;
}
```

для `x = INT_MAX` по обычной арифметике должна вернуть $0$, если `INT_MAX + 1` «переполнится» в отрицательное число. У GCC 13 (и с `-O0`, и с `-O2`) вызов `bigger(INT_MAX)` вернул $1$: переполнение знакового целого — неопределенное поведение, поэтому компилятор считает, что `x + 1` всегда больше `x`, и заменяет всё выражение единицей. С флагом `-fwrapv`, который делает переполнение определенным (по модулю $2^n$), тот же вызов вернул $0$. Ответ меняется от флагов компилятора, и ни один из них не ошибка компилятора.
:::

::: {.remark #rem:lec03:infinite-loop tag="подводный камень"}
Есть похожее разрешение и для циклов. Стандарт (с C11) позволяет компилятору считать, что цикл завершается, если его условие не константа, а тело не делает ввода-вывода и не обращается к памяти с пометкой `volatile`. В программе

```c
#include <stdio.h>

int main(void)
{
    unsigned x = 0;
    while (x >= 0) {
        x = x + 1;
    }
    printf("цикл закончился\n");
    return 0;
}

void never_called(void)
{
    printf("эту строку никто не печатал\n");
}
```

условие `x >= 0` для беззнакового `x` истинно всегда, и цикл бесконечный. Собранная GCC 13 или Clang 18 с `-O0`, программа зависает. Clang 18 с `-O2` (в режимах C11 и новее) выбрасывает и цикл, и всё, что за ним, раз до этого кода «невозможно» дойти. Выполнение уходит в код, который лежит в памяти следом, и программа печатает `эту строку никто не печатал`, хотя `never_called` нигде не вызывается. С `-std=c99`, где такого разрешения нет, программа зависает и у Clang. Бесконечный цикл здесь — ошибка программиста, и `gcc -Wextra` её замечает: `comparison of unsigned expression in '>= 0' is always true`.
:::

## Представление целых чисел

Размер и знак выбраны; осталось понять, что именно лежит в этих байтах. Целые хранятся в двоичной позиционной системе, и байты одного числа идут в памяти подряд, без промежутков: дыры между ними ничего бы не дали.

### Порядок байтов

Число из нескольких байтов занимает несколько адресов, и нужно решить, в каком порядке класть байты. Удобно записывать байты в шестнадцатеричной системе: в байте $8$ бит, то есть ровно две шестнадцатеричные цифры. Число $\mathrm{0A0B0C0D}_{16}$ состоит из байтов $\mathrm{0A}$ (старший), $\mathrm{0B}$, $\mathrm{0C}$, $\mathrm{0D}$ (младший).

::: {.definition #def:lec03:endianness title="порядок байтов"}
При порядке *little-endian* по младшему адресу лежит младший байт числа, дальше байты всё более старшие. При порядке *big-endian* по младшему адресу лежит старший байт.
:::

```{.tikz #fig:lec03:endianness caption="Число $\mathrm{0A0B0C0D}_{16}$ из четырех байтов по адресам $100$–$103$ при двух порядках байтов"}
\begin{tikzpicture}[cell/.style={draw, thick, minimum width=1.2cm, minimum height=0.7cm, font=\ttfamily}, addr/.style={font=\small, nbgray}]
  \foreach \a [count=\i from 0] in {100,101,102,103} {
    \node[addr] at (1.2*\i, 2.3) {\a};
  }
  \node[anchor=east, font=\small] at (-0.8, 1.4) {little-endian};
  \foreach \b [count=\i from 0] in {0D,0C,0B,0A} {
    \node[cell, fill=nbblue!12] at (1.2*\i, 1.4) {\b};
  }
  \node[anchor=east, font=\small] at (-0.8, 0.4) {big-endian};
  \foreach \b [count=\i from 0] in {0A,0B,0C,0D} {
    \node[cell, fill=nborange!15] at (1.2*\i, 0.4) {\b};
  }
  \draw[->, nbgray] (-0.6, -0.4) -- (4.2, -0.4) node[right, font=\small] {адреса растут};
\end{tikzpicture}
```

На рис. [-@fig:lec03:endianness] одно и то же число при двух порядках. Оба варианта существовали в реальных процессорах, поэтому стандарт C порядок байтов не фиксирует, он зависит от аппаратуры. Процессоры Intel и AMD архитектуры x86 — little-endian, мейнфреймы IBM — big-endian, а часть процессоров (например, ARM) умеет работать в обоих порядках, его задает флаг. Порядок битов внутри байта стандарт тоже не гарантирует, а узнать его программой часто невозможно: адрес есть только у байта целиком.

Пока число читает тот же процессор, что его записал, порядок не важен. Он становится важен, когда байты переезжают на другую машину. Компьютеры с разным порядком байтов обмениваются пакетами по сети, и если каждый будет класть числа в пакет в своем порядке, они друг друга не поймут.

::: {.definition #def:lec03:network-order title="сетевой порядок байтов"}
*Сетевой порядок байтов* (network byte order) — порядок, в котором числа записываются в пакеты сетевых протоколов; это big-endian. Машина с другим *собственным* порядком переставляет байты при отправке и при получении.
:::

В системах семейства UNIX для этого есть функции `htonl` и `ntohl` («host to network» и обратно) из `arpa/inet.h`; в стандартной библиотеке C их нет.

### Дополнительный код

С неотрицательными числами всё ясно: двоичная запись. Для отрицательных нужен знак, и на него приходится потратить бит из того же бюджета: в $n$-битном числе остается $n - 1$ бит на значение. Как именно кодировать, вопрос неочевидный.

Первая мысль — *прямой код*: старший бит — знак, остальные — модуль. Но тогда сложение устроено сложно: складывать модули, если знаки одинаковые, и вычитать меньший из большего, если разные; а у нуля два кода, $+0$ и $-0$. В *обратном коде* $-x$ получается инвертированием всех битов $x$; у нуля там тоже два кода. Удобнее всего *дополнительный код*.

::: {.definition #def:lec03:twos-complement title="дополнительный код"}
В *дополнительном коде* из $n$ бит целое $x$ с $-2^{n-1} \le x \le 2^{n-1} - 1$ записывается так: при $x \ge 0$ — двоичная запись $x$, при $x < 0$ — двоичная запись числа $2^n - |x|$. Старший бит (номер $n - 1$) — знаковый: он равен $1$ ровно у отрицательных чисел. Биты с номерами от $0$ до $n - 2$ — значение.
:::

Пример: в $8$ битах $-5$ записывается как $256 - 5 = 251 = 11111011_2$. Таблица для $n = 3$ сравнивает все три способа: столбцы — значения, которые один и тот же набор битов означает в каждом коде.

| биты | без знака | прямой код | обратный код | дополнительный код |
| --- | --- | --- | --- | --- |
| `000` | $0$ | $0$ | $0$ | $0$ |
| `001` | $1$ | $1$ | $1$ | $1$ |
| `010` | $2$ | $2$ | $2$ | $2$ |
| `011` | $3$ | $3$ | $3$ | $3$ |
| `100` | $4$ | $-0$ | $-3$ | $-4$ |
| `101` | $5$ | $-1$ | $-2$ | $-3$ |
| `110` | $6$ | $-2$ | $-1$ | $-2$ |
| `111` | $7$ | $-3$ | $-0$ | $-1$ |

В дополнительном коде у каждого набора битов свое значение, ноль один, а неотрицательные числа записаны так же, как беззнаковые. Главное его достоинство — сложение.

::: {.proposition #prop:lec03:twos-add title="сложение в дополнительном коде"}
Пусть $a$, $b$ и $a + b$ лежат в диапазоне $[-2^{n-1}, 2^{n-1} - 1]$, и $[x]$ — дополнительный код $x$ как беззнаковое число от $0$ до $2^n - 1$. Тогда $[a + b] = ([a] + [b]) \bmod 2^n$. Кроме того, если $x$ и $-x$ лежат в том же диапазоне, $[-x]$ получается из $[x]$ инвертированием всех битов и прибавлением $1$ (по модулю $2^n$).
:::

::: proof
При $x \ge 0$ имеем $[x] = x$, при $x < 0$ имеем $[x] = 2^n - |x| = 2^n + x$. В обоих случаях $[x] \equiv x \pmod{2^n}$ и $0 \le [x] < 2^n$, то есть $[x]$ — остаток от деления $x$ на $2^n$. Значит, $[a] + [b] \equiv a + b \equiv [a + b] \pmod{2^n}$, а остаток от деления на $2^n$ однозначен, откуда $([a] + [b]) \bmod 2^n = [a + b]$.

Инвертирование всех битов $n$-битного числа $y$ дает $2^n - 1 - y$: в сумме с $y$ каждый разряд равен $1$. Поэтому инвертирование $[x]$ и прибавление $1$ дают $2^n - [x] \equiv -x \pmod{2^n}$, и по модулю $2^n$ это и есть $[-x]$.
:::

Проверим на $n = 8$: $-5 + 7$. Коды $251$ и $7$, сумма $258$, по модулю $256$ получаем $2 = [2]$. Перенос из старшего разряда просто отбрасывается. Значит, процессору достаточно одного сумматора по модулю $2^n$ и для беззнаковых, и для знаковых чисел, а вычитание сводится к сложению с $[-b]$. Проверим и второе правило: $5 = 00000101_2$, инверсия $11111010_2$, плюс один — $11111011_2 = 251 = [-5]$.

::: {.remark #rem:lec03:min-value tag="корнер-кейс"}
Диапазон несимметричен: в $n$ битах есть $-2^{n-1}$, но нет $2^{n-1}$. В $8$ битах $-128 = 10000000_2$, а инвертирование и прибавление единицы дают тот же код $10000000_2$: у $-128$ нет положительной пары. Поэтому, например, модуль самого маленького `int` в `int` не помещается.
:::

Ранние стандарты C требовали только, чтобы у знакового числа был один знаковый бит, а способ кодирования оставляли реализации: допускались прямой, обратный и дополнительный код. Машины с прямым и обратным кодом вымерли, и C23 сделал дополнительный код обязательным. Требования к языку меняются вместе с машинами, на которых он работает.

## Логический тип

В первом C логического типа не было, хватало целых: $0$ означает «ложь», любое ненулевое значение — «истина». Так и работают условия в C до сих пор. Но логические значения нужны почти в каждой программе, поэтому почти в каждой большой программе появлялся свой логический тип, часто под именем `bool`:

```c
typedef int bool;
#define true 1
#define false 0
```

Здесь `typedef` вводит новое имя для типа `int`, а `#define` — текстовые замены для препроцессора. Когда вариантов стало много, логичным стало закрепить один в стандарте, как словари со временем закрепляют слово, которым уже все пользуются. Но объявить `bool` ключевым словом, как `int`, было нельзя: все программы, где `bool` уже определен, как выше, перестали бы компилироваться, ведь назвать свой тип или переменную ключевым словом нельзя (как нельзя назвать переменную `for`). Молодой язык, на котором еще мало написано, может позволить себе ломать совместимость ради скорости развития. Язык с миллионами программ так поступить не может: это ставит под удар всех, кто на нём пишет. Язык, который не меняется вовсе, умирает. C нашел третий путь через зарезервированные имена.

::: {.definition #def:lec03:reserved-names title="зарезервированные идентификаторы"}
Идентификаторы, которые начинаются с подчеркивания и заглавной буквы (`_Bool`) или с двух подчеркиваний (`__func__`), *зарезервированы* за реализацией: программа не должна их объявлять. Стандарт и компиляторы вводят под такими именами новые возможности и служебные объекты.
:::

Так в C99 появился тип `_Bool`: беззнаковый целый тип со значениями $0$ и $1$. Старые программы это не сломало: имя `_Bool` они использовать не имели права. Красивые имена `bool`, `true`, `false` дал новый заголовочный файл `stdbool.h`. Программа, которая его подключает, заведомо новая: раньше такого файла не было. Значит, своего `bool` в ней нет, и новые имена ничего не ломают. Тем же способом C11 ввел `_Thread_local`, `_Generic`, `_Noreturn` и другие.

::: {.definition #def:lec03:bool title="логический тип"}
*Логический тип* `_Bool` (C99) — беззнаковый целый тип со значениями $0$ и $1$. При записи в него любого ненулевого значения получается $1$, нулевого — $0$. В C99–C17 имена `bool`, `true`, `false` дают `#include <stdbool.h>`; в C23 `bool`, `true` и `false` — ключевые слова языка.
:::

::: {.example #ex:lec03:bool title="значения _Bool"}
```c
#include <stdbool.h>
#include <stdio.h>

int main(void)
{
    _Bool b = 5;
    bool done = false;
    printf("%d %d %d\n", b, done, true);
    return 0;
}
```

Программа печатает `1 0 1`: при записи $5$ в `_Bool` получается $1$. В отличие от «самодельного» `bool` через `typedef int`, где переменная `b` хранила бы $5$. Занимает `_Bool`, как и любой объект, целое число байтов, обычно один: `sizeof(_Bool)` у GCC на x86-64 равен $1$.
:::

В C23 переходный период закончился: `bool`, `true` и `false` стали ключевыми словами, и программе на C23 `stdbool.h` не нужен. Обратная сторона видна на старом коде: определение `typedef int bool;` в режиме `-std=c17` компилируется, а в режиме C23 GCC выдает ошибку `two or more data types in declaration specifiers`. Так язык и развивается: новую возможность сначала обкатывают, не ломая старых программ, а когда ей все пользуются, вводят насовсем.

Похожий путь прошли комплексные числа: тип `_Complex` и заголовок `complex.h` появились в C99, а в C11 их поддержка стала необязательной, потому что нужны они немногим.

# Практика

::: {.problem #prob:lec03:no-include}
Из программы «Hello, world» убрали первую строку `#include <stdio.h>`. Что сообщит компилятор и почему? Что изменится, если вместо этого убрать строку `return 0;`?
:::

::: solution
*Ключ:* `#include` вставляет в текст объявление `printf`; без него компилятор видит вызов функции, о которой ничего не знает.

Без `#include` в программе нет объявления `printf`: имени, типов параметров и результата. По стандарту C99 вызов необъявленной функции — ошибка, компилятор обязан выдать диагностику. GCC 13 выдает предупреждение `implicit declaration of function 'printf'` (и подсказывает подключить `stdio.h`), GCC 14 — ошибку. Даже если программа соберется, компилятор не проверял вызов: он не знал, какие аргументы ждет функция.

Без `return 0;` программа правильная: при выходе из `main` через закрывающую скобку она возвращает $0$ (C99 и новее).
:::

::: {.problem #prob:lec03:warnings}
В файле `main.c` внутри `main` написали `int unused = 1;` и забыли поставить точку с запятой после `return 0`. Что произойдет при сборке командами `gcc main.c -o main`, `gcc -Wall -Wextra main.c -o main` и `gcc -Wall -Wextra -Werror main.c -o main`, если сначала исправить пропущенную точку с запятой, а `unused` оставить?
:::

::: solution
*Ключ:* ошибка синтаксиса всегда останавливает сборку; предупреждение при `-Wall -Wextra` не мешает создать файл, а `-Werror` превращает его в ошибку.

Пока нет `;` после `return 0`, любая из трех команд завершается ошибкой (`expected ';'`), исполняемый файл `main` не создается. Когда `;` возвращена, программа синтаксически корректна, но `unused` нигде не используется: `gcc main.c -o main` собирает файл молча, `gcc -Wall -Wextra main.c -o main` печатает предупреждение `-Wunused-variable` и всё равно создает `main`, а `gcc -Wall -Wextra -Werror main.c -o main` превращает это предупреждение в ошибку и не создает исполняемый файл.
:::

::: {.problem #prob:lec03:format}
Напиши вызовы `printf`, которые печатают ровно две строки (значения $7$ и $4$ подставь через `%d`, разность пусть вычисляет программа):

```
Путь: D:\games\new
Счет 7:4, разница 3, это 75% побед
```
:::

::: solution
*Ключ:* в строковой константе каждый `\` начинает управляющую последовательность, а каждый `%` в форматной строке — спецификатор, поэтому оба удваиваются.

```c
printf("Путь: D:\\games\\new\n");
printf("Счет %d:%d, разница %d, это 75%% побед\n", 7, 4, 7 - 4);
```

Если написать `"D:\games\new"`, то `\g` — неизвестная последовательность (GCC предупреждает `unknown escape sequence: '\g'`), а `\n` в `\new` — перевод строки: напечатается `D:games`, а `ew` уйдет на следующую строку. Если написать `75%` без удвоения, `printf` примет `%` и следующие за ним символы за спецификатор и напечатает не то.
:::

::: {.problem #prob:lec03:storage}
Какой класс памяти подходит для данных?

- (а) Число вызовов функции за всю работу программы.
- (б) Частичные суммы внутри функции, вычисляющей $\sin x$ рядом.
- (в) Числа, которые пользователь вводит, пока не введет ноль; все они нужны до конца обработки.
- (г) Счетчик цикла внутри функции, к которому обращаются миллионы раз.
:::

::: solution
*Ключ:* спросить, известны ли до запуска объем данных и момент, когда они перестанут быть нужны.

(а) Значение должно сохраняться между вызовами и жить всю программу: статическая (глобальная переменная).

(б) Нужны только пока работает функция, объем известен по тексту функции: автоматическая (локальные переменные).

(в) Сколько чисел будет, неизвестно до запуска: динамическая.

(г) Локальная переменная, то есть автоматическая; так как к ней часто обращаются, её выгодно держать в регистре. Это можно подсказать словом `register`, но решает компилятор, и обычно он поместит её в регистр сам.

*Ответ:*

- (а) статическая;
- (б) автоматическая;
- (в) динамическая;
- (г) автоматическая, хорошо подходит для регистра.
:::

::: {.problem #prob:lec03:sizes-allowed}
Байт $8$-битный. Какие наборы размеров (в байтах, порядок `char`, `short`, `int`, `long`, `long long`) допускает стандарт?

- (а) $1, 2, 2, 4, 8$.
- (б) $1, 4, 4, 4, 8$.
- (в) $1, 2, 4, 4, 4$.
- (г) $1, 2, 8, 4, 8$.
- (д) $2, 2, 4, 8, 8$.
:::

::: solution
*Ключ:* проверить три вещи по определению [-@def:lec03:int-types]: `char` ровно $1$ байт, нижние границы ($2$, $2$, $4$, $8$ байтов для `short`, `int`, `long`, `long long`), неубывание по ряду.

(а) Всё выполнено: типичная $16$-битная машина.

(б) Нижние границы выполнены ($4 \ge 2$), порядок не нарушен. Допустимо.

(в) `long long` — $4$ байта, а нужно не меньше $8$ ($64$ бит). Нельзя.

(г) `int` длиннее `long`: `long` не вместит всех значений `int`. Нельзя.

(д) `sizeof(char)` всегда $1$. Нельзя.

*Ответ:* допустимы (а) и (б).
:::

::: {.problem #prob:lec03:behavior}
К какой категории поведения относится каждое утверждение?

- (а) `sizeof(char)` равен $1$.
- (б) `sizeof(int)` на данной машине равен $4$.
- (в) В вызове `printf("%d %d\n", f(), g())` функция `f` вызывается раньше `g`.
- (г) Значение выражения `INT_MAX + 1`.
- (д) Простой `char` на данной машине знаковый.
- (е) Программа без `return` в `main` возвращает $0$.
:::

::: solution
*Ключ:* различать, обязана ли реализация документировать выбор (определяется реализацией), может ли выбирать произвольно (неуточненное) или стандарт вообще ничего не требует (неопределенное).

- (а) Определено стандартом.
- (б) Размер `int` выбирает реализация и документирует его: определяется реализацией.
- (в) Порядок вычисления аргументов не задан и может отличаться даже у одного компилятора: неуточненное (GCC и Clang печатают по-разному, пример [-@ex:lec03:unspecified]).
- (г) Переполнение знакового `int`: неопределенное.
- (д) Определяется реализацией.
- (е) Определено стандартом (с C99).

*Ответ:*

- определено — (а), (е);
- определяется реализацией — (б), (д);
- неуточненное — (в);
- неопределенное — (г).
:::

::: {.problem #prob:lec03:bytes}
- (а) Переменная типа `int` из $4$ байтов со значением $2026$ лежит по адресам $200$–$203$. Какие байты лежат по каждому адресу на little-endian и на big-endian машине?
- (б) По адресам $200$–$203$ лежат байты $01$, $02$, $00$, $00$ (шестнадцатеричные). Какое число типа `int` здесь записано на little-endian машине, а какое на big-endian?
:::

::: solution
*Ключ:* сначала записать число в шестнадцатеричной системе с ведущими нулями до $8$ цифр, потом резать на байты по две цифры.

(а) $2026 = 7 \cdot 256 + 14 \cdot 16 + 10 = \mathrm{7EA}_{16}$, то есть $\mathrm{000007EA}_{16}$: байты от старшего $00$, $00$, $07$, $\mathrm{EA}$. Little-endian кладет с младшего: по адресам $200$, $201$, $202$, $203$ лежат $\mathrm{EA}$, $07$, $00$, $00$. Big-endian — со старшего: $00$, $00$, $07$, $\mathrm{EA}$.

(б) На little-endian по адресу $200$ младший байт, число $00000201_{16} = 2 \cdot 256 + 1 = 513$. На big-endian по адресу $200$ старший байт, число $01020000_{16} = 2^{24} + 2 \cdot 2^{16} = 16\,777\,216 + 131\,072 = 16\,908\,288$.

*Ответ:*

- (а) little-endian: $\mathrm{EA}, 07, 00, 00$; big-endian: $00, 00, 07, \mathrm{EA}$.
- (б) $513$ и $16\,908\,288$.
:::

::: {.problem #prob:lec03:twos}
- (а) Запиши $-100$ в дополнительном коде из $8$ бит.
- (б) Какое число означает код $11100111_2$ в $8$-битном дополнительном коде и какое — как беззнаковое?
- (в) Каков диапазон $16$-битного знакового целого в дополнительном коде?
- (г) Запиши $8$-битные дополнительные коды чисел $12$, $-1$, $-17$ и $-128$ двумя шестнадцатеричными цифрами.
:::

::: solution
(а) $2^8 - 100 = 156 = 128 + 16 + 8 + 4 = 10011100_2$. Проверка по правилу инверсии: $100 = 01100100_2$, инверсия $10011011_2$, плюс один — $10011100_2$.

(б) *Ключ:* знаковый бит равен $1$, значит, число отрицательное и код равен $2^8 - |x|$. Как беззнаковое $11100111_2 = 128 + 64 + 32 + 4 + 2 + 1 = 231$. Как знаковое $x = 231 - 256 = -25$.

(в) От $-2^{15}$ до $2^{15} - 1$, то есть от $-32\,768$ до $32\,767$.

(г) Каждая шестнадцатеричная цифра — четыре бита. $12 = 0000\,1100_2 = \mathrm{0C}_{16}$. Для отрицательных берем $256 - |x|$: $-1 \mapsto 255 = 1111\,1111_2 = \mathrm{FF}_{16}$, $-17 \mapsto 239 = 1110\,1111_2 = \mathrm{EF}_{16}$, $-128 \mapsto 128 = 1000\,0000_2 = 80_{16}$.

*Ответ:*

- (а) $10011100_2$;
- (б) $-25$ и $231$;
- (в) $[-32\,768, 32\,767]$;
- (г) $\mathrm{0C}$, $\mathrm{FF}$, $\mathrm{EF}$, $80$.
:::

::: {.problem #prob:lec03:bool}
Что напечатает программа?

```c
#include <stdio.h>

int main(void)
{
    _Bool a = -3;
    _Bool b = 0;
    printf("%d %d %d\n", a, b, a + a);
    return 0;
}
```
:::

::: solution
*Ключ:* при записи в `_Bool` любое ненулевое значение становится $1$. Значит, `a` равно $1$, `b` равно $0$, а `a + a` — обычное целое сложение $1 + 1 = 2$: `_Bool` хранит только $0$ и $1$, но сумма двух таких значений уже имеет тип `int`. Программа печатает `1 0 2`.
:::

::: {.problem #prob:lec03:bool-c23}
Почему в C99 логический тип назвали `_Bool`, а не `bool`, и что случится со старой программой, где есть строка `typedef int bool;`, при компиляции по стандарту C23?
:::

::: solution
Имя `bool` многие программы уже определяли сами; ключевое слово `bool` сломало бы их. Имя `_Bool` зарезервировано за реализацией, правильные программы его не использовали, поэтому его введение ничего не сломало. В C23 `bool` — ключевое слово, и `typedef int bool;` больше не компилируется (GCC: `two or more data types in declaration specifiers`); такую программу собирают с `-std=c17` или убирают самодельное определение.
:::

# Итоги

- C создан для UNIX: язык близок к машине, переносим на уровне исходного кода, и его стандарты (C89, C99, C11, C18, C23) пишет комитет как договоренность разработчиков компиляторов.
- Чтобы вызвать функцию, компилятору нужно только её объявление; объявления библиотечных функций вставляет препроцессор директивой `#include`, а `main` возвращает системе код завершения: $0$ — успех.
- В форматной строке `printf` обратный слэш начинает управляющую последовательность, `%` — спецификатор; чтобы напечатать их самих, их удваивают.
- Класс памяти определяется тем, что известно до запуска: статическая живет всю программу, автоматическую на время функции выделяет компилятор, динамической управляет программист, когда неизвестен объем или время жизни.
- Размеры целых типов выбирает реализация; гарантированы только `sizeof(char) == 1`, нижние границы $16$, $16$, $32$, $64$ бита для `short`, `int`, `long`, `long long` и неубывание по этому ряду.
- Знаковость `char`, размер `int` и порядок байтов зависят от платформы; при неопределенном поведении, например переполнении `int`, стандарт ничего не требует, и компилятор оптимизирует программу так, будто его не бывает.
- Отрицательное $x$ в дополнительном коде из $n$ бит — это $2^n - |x|$; один сумматор по модулю $2^n$ складывает и знаковые, и беззнаковые числа, а с C23 дополнительный код обязателен.
- Новые возможности C вводит под зарезервированными именами (`_Bool`) и отдельными заголовками (`stdbool.h`), а когда все к ним привыкли, делает ключевыми словами (`bool` в C23).
