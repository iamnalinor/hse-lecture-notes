# Процесс работы агента

Правила процесса для любой задачи в репозитории: конспект, страница сайта, код пайплайна, фронтенд. Они не зависят от того, какие скиллы установлены в сессии. Всё нужное пересказано здесь и в `context/style/`. Если нужен полный текст исходного скилла, `./scripts/fetch_skills.sh` скачивает закрепленные версии в `.cache/skills/` (каталог не коммитится).

Правила адаптированы, а не скопированы. При конфликте с `CLAUDE.md` или прямым указанием владельца верно указание владельца.

## П0. Материалы владельца — сразу в контекст

Ссылку, файл или факт, который прислал владелец (репо семинаристов, запись, слайды, даты), в тот же ход записать в `context/courses/<course>.md` (раздел источников) и при необходимости в `context/sources.md`: путь или URL, что внутри, к каким лекциям относится. Если материал меняет работу (например, дает семинары к уже написанным конспектам), сразу поставить задачу в очередь `context/debt.md`. Не записанное в контекст теряется при сжатии разговора (так 22.11.2026 потерялись репо семинаров АиЯ).

Контекст живет в репозитории, а окружение для каждой задачи создается заново: `sources/`, `build/`, `.cache/`, установленные пакеты в новой сессии пусты. Поэтому в контекст не пишем состояние окружения («скачано», «склонировано», «лежит локально», «на этой машине curl дает 403»). Пишем то, что переживет пересоздание: откуда взять (URL, id видео, команда скачивания, кто прислал и когда), куда положить (путь в `sources/` — это договоренность о раскладке, а не факт наличия) и что внутри. Материал, который нельзя скачать заново (файл прислал владелец), помечаем: «прислал владелец, просить снова».

## П1. Сначала план, потом работа

Задачу больше одного файла сначала разбей на этапы. У каждого этапа должен быть проверяемый результат: что изменится, чем это проверить, какие файлы затронуты. Крупный план согласуй с владельцем до работы. Планы Superpowers и служебные отчеты выполнения храним только локально в игнорируемых `.superpowers/` или `docs/superpowers/`; в Git их не добавляем. Если владелец просил останавливаться после этапов, после каждого этапа покажи результат (скриншоты, diff, команды проверки) и жди ответа.

Если требование неясно, спроси один конкретный вопрос. Не додумывай молча. Если пришлось выбрать разумное значение по умолчанию, назови его в отчете.

## П2. Доказательство перед словом «готово»

При любой значимой правке фронтенда сними в браузере каждый изменённый пользовательский сценарий. Собери скриншоты в отдельном документе ChatGPT Space по задаче и покажи владельцу ссылку на него в отчёте. Под каждым снимком укажи действие, видимый результат и версию сайта. Если менялась адаптивная вёрстка, покажи результат на телефоне и компьютере. Для изменений поведения покажи нужные состояния по порядку, а при использовании тестовых данных отметь это в подписи. При следующих правках в той же задаче дополняй этот документ.

Не пиши «работает», «тесты проходят» или «исправлено», пока в этом же сообщении не запустил команду, которая это доказывает, и не прочитал её вывод целиком.

| Утверждение | Чем доказать | Чего недостаточно |
| --- | --- | --- |
| конспект корректен | `uv run scripts/lint.py <файл>` без ошибок, `build.py --only <файл>` без overfull | «линтер раньше проходил» |
| сайт собирается | `bun run lint && bun run test && bun run build` из `web/` | только `tsc` |
| страница выглядит хорошо | скриншоты Playwright 390 и 1280 px, просмотренные глазами | «CSS выглядит правильно» |
| баг исправлен | воспроизведение исходного симптома больше не срабатывает | «код поменял» |
| сабагент сделал работу | `git diff` показывает изменения, проверки пройдены | отчет сабагента «успешно» |

Если проверка не прошла, так и напиши и приложи вывод.

Связанные части модуля группируем в папки по назначению, а не размножаем общий префикс в плоском каталоге. Frontend-тесты — в `web/tests/` с деревом, соответствующим `web/src/`; общие фикстуры — в `web/tests/support/`, браузерные проверки — в `web/tests/e2e/`.

## П3. Тест вперед для кода

Правишь `filters/`, `scripts/` или `web/src/` — сначала тест, который падает без правки (`tests/`, `*.test.ts`). Потом правка, потом тест зеленый. Для чисто визуальной правки вместо теста делай скриншот до и после.

## П4. Отладка: сначала причина

Пока не воспроизвел баг и не понял механизм, не чини. Последовательность: воспроизвести → сузить до минимального случая → назвать причину одной фразой → чинить причину, а не симптом → проверить по П2. Если две попытки починить не сработали, остановись и пересмотри гипотезу.

## П5. Ревью отдельным агентом

После каждого этапа, перед коммитом в `main`, запусти ревью свежим сабагентом. Он не видел истории сессии и получает только:

- что сделано и зачем (2–5 строк);
- требования (пункты плана или ссылка на них);
- диапазон коммитов `BASE..HEAD`;
- чеклист по типу работы: конспект — `prompts/review.md`; страницы подготовки — `prompts/prep-review.md`; сайт — `style/design.md` + `site.md`; код — корректность, тесты, простота.

Ответ ревьюера делится на «критично», «важно» и «мелочь». Критичное и важное исправь до следующего этапа. Мелочи запиши. С ревьюером можно спорить, но с доводами. Чужое замечание проверь, прежде чем выполнять: ревьюер тоже ошибается.

## П6. Сабагенты и лимиты

- Механика (распознать PDF без текстового слоя, перенести блоки по шаблону, массово переименовать) — модель подешевле (Sonnet). Решения о содержании, математика и ревью — основная модель.
- Задание сабагенту самодостаточно: пути к файлам, критерий готовности, формат отчета. Историю сессии он не видит.
- Агентов запускай по одному, не параллельно, и порядок расписывай заранее (указание владельца 22.11.2026: экономим лимиты). Мелкие правки ведущий делает сам, мелочи пачкой отдает одному Sonnet.
- Отчет сабагента не доказательство (П2): проверь diff.

Спорные решения по содержанию — не молча. Если связный текст и лекция тянут в разные стороны (Р30 в `recommendations.md`) или задача допускает два разумных варианта, которые владелец заметит, сабагент пишет их в отчет пунктом «Вопросы владельцу», а ведущий задает их владельцу до коммита. Без ответа коммитится разумный вариант, но вопрос остается в сообщении владельцу.

## П7. Ветка и завершение

Работа идет в своей ветке. В `main` попадает только через PR со squash-мержем (`CLAUDE.md`). Перед PR должны пройти `uv run scripts/lint.py`, `uv run pytest -q`, `uv run scripts/build.py --strict`, а при правках в `web/` еще `bun run lint` и `bun run test`. Сообщения коммитов пишутся на английском.
