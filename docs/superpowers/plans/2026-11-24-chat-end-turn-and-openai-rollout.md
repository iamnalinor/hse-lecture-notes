# Chat End Turn and OpenAI Rollout Implementation Plan

> **Заменён:** актуальные итоговые решения и весь порядок реализации находятся в [новом едином плане](./2026-11-24-chat-metadata-context-and-openai-rollout.md). Этот документ сохранён как история обсуждения; его альтернативы и этапы не исполнять.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Работать последовательно; ревью — одним свежим агентом по правилам репозитория.

**Goal:** Перевести production на OpenAI API с бюджетом $15 за скользящие 7 дней и добавить скрытый завершающий инструмент с названием чата и предложением следующего сообщения.

**Architecture:** Существующий OpenAI Responses provider работает напрямую, без Codex SOCKS5 proxy. Агентный цикл заканчивается успешно после валидного `end_turn({ title, suggestion })`, следующего за ответом. Метаданные сохраняются вместе с результатом хода; клиент получает название и саджест отдельно от Markdown.

**Tech Stack:** Cloudflare Workers / Durable Objects, D1 SQLite, Bun, TypeScript, Responses API, React, Vitest, Playwright.

**Spec:** Раздел «Согласованное поведение и предлагаемые параметры» в этом документе фиксирует требования беседы и отдельно помеченные решения реализации.

**Статус:** Только план. Пользователь запретил реализацию до отдельного явного указания. Создание этого документа не разрешает менять код, production policy, секреты или активную версию Worker.

## Global Constraints

- Внутренний инструмент называется `end_turn`; ровно два аргумента: `title` и `suggestion`.
- Пользователь согласовал `title: null` для сохранения названия. В первом успешном ходе название обязательно.
- Схема `end_turn` единая во всех ходах: оба поля nullable; обязательность первого непустого title обеспечивают инструкция и harness, а не смена схемы.
- Системные инструкции постоянны. Контекст страницы/оглавление и актуальное состояние названия передаются рядом с текущим вопросом; снимок прежнего контекста не пересобирается по текущей навигации.
- Саджест должен опираться на уже написанный ответ и звучать как следующая реплика пользователя.
- Саджест предпочтителен: если нет узкого продолжения, предложить полезный общий следующий шаг. `suggestion: null` оставлять для случаев, когда осмысленного предложения действительно нет; frontend показывает обычный placeholder.
- Согласованные лимиты будущего цикла: `maxToolRounds: 6`, `maxToolCalls: 12`; прежний предел 60 секунд сохраняется. Исправления протокола входят в эти лимиты.
- Новые согласованные пределы истории: `maxHistoryMessages: 15`, `maxHistoryChars: 50_000` вместо текущих 16 / 24_000. Это два одновременных ограничения, срабатывает первое достигнутое; не заменять их ранее предложенными 64 / 96_000.
- Инструмент и его аргументы не показываются в Markdown и поисковых шагах.
- Production использует `LLM_PROVIDER=openai`, ключ из корневого `.env`, прямой `https://api.openai.com/v1/responses`.
- Недельный общий лимит — `15_000_000` микродолларов. Не сбрасывать накопленные расходы и пользовательские квоты.
- Сохранять существующие модели, историю, авторизацию и тарифные категории; доступность моделей проверить перед переключением.
- Ключ передавать в Worker secret через stdin; не печатать, не передавать аргументом команды и не коммитить.
- Тесты перед изменением поведения. Полный backend test/typecheck, frontend lint/test/build и браузерные сценарии перед завершением соответствующих этапов.

## Review Focus

1. `end_turn` до ответа, после него дополнительный текст, пропущенный или повторный вызов: неверные метаданные не публикуются, цикл ограничен.
2. Stop, timeout, EOF, исчерпание бюджета: текст сохраняется, частичные метаданные не применяются; все оплаченные раунды учитываются.
3. Одновременные finalize/retry/reconnect: название и саджест применяются один раз к правильному сообщению.
4. Поздний результат при переключении чата, начатом вводе или добавленной цитате: саджест не заменяет пользовательский черновик.
5. Следующий CI deploy и откат провайдера: OpenAI остаётся выбранным явно, Codex proxy не используется запросами OpenAI, история и расход сохраняются.

## Согласованное поведение и предлагаемые параметры

### Контракт завершения

- В обычных раундах доступны учебные инструменты и `end_turn`, `tool_choice: "required"`, `parallel_tool_calls: false`.
- В последнем разрешённом раунде разрешён вызов только `end_turn`, с `tool_choice: { type: "function", name: "end_turn" }`. Определения всех инструментов в `tools` оставлять прежними: ограничивать выбор, а не менять префикс ради финального раунда.
- У `end_turn` — `strict: true`, `additionalProperties: false`, `required: ["title", "suggestion"]`.
- Тип `title` всегда `["string", "null"]`; схему не менять между первым и последующими ходами. Если у чата нет `generated_title`, рядом с вопросом передать `title_required: true`; постоянная инструкция требует название. Harness отклоняет `title: null` с причиной `first_title_required`, возвращает скрытый результат инструмента и использует общий ограниченный путь исправления. Только непустое название позволяет успешный первый ход; это относится и к старому чату без названия после прерванной генерации.
- `suggestion` всегда имеет тип `["string", "null"]`. Оба поля присутствуют. `title: null` означает «сохранить название»; `suggestion: null` означает «нет предложения», frontend возвращается к обычному placeholder. Инструкция модели: стараться предложить полезную следующую реплику; если конкретное продолжение неочевидно, допустимо общее, но уместное «Покажи на примере» / «Дай похожую задачу». Не выдумывать намерение пользователя и не продолжать разговор бессодержательной фразой ради непустого поля. `null` — только когда осмысленного продолжения действительно нет.
- Пустые строки не заменяют `null`. Сервер проверяет непустое название, сохраняет существующий предел 48 Unicode-символов и нормализацию.
- **Предложение реализации:** саджест — одна реплика до 160 Unicode-символов, обычный текст без служебной разметки. Пустая строка и превышение длины — ошибка аргументов.
- Название меняется при смене цели или темы, если прежнее название уже вводит в заблуждение. Перефразирование ради перефразирования не нужно. Текущее название передаётся модели.
- Успешный ход требует `response.completed`, отсутствия усечения, валидного `end_turn` и текста ответа до него. Пустой/пробельный текст, reasoning и аргументы инструмента не являются ответом. Одной непустой поисковой преамбулы перед обычным инструментом недостаточно. Проверка порядка структурная: после последнего учебного инструмента должен появиться текст ответа; сервер не обещает определить его смысловую полноту по длине или регулярке.
- В обычном ходе текст и `end_turn` могут прийти в одном запросе. Второй запрос не обязателен.
- **Предложение восстановления:** не больше одного корректирующего раунда на ход, только при оставшихся времени, резерве и раундах. После повторного нарушения остановить цикл; бесконечного `while (!endTurn)` нет. Это продолжение известного ответа, а не повтор сетевого запроса с неизвестным результатом.
- Если модель вернула завершённый текст без завершающего вызова, сохранить уже показанный ответ и запросить только метаданные через forced `end_turn`. В этом режиме дополнительные текстовые delta не показывать и не приписывать к ответу; их наличие означает повторное нарушение. Если `response.completed` не было, ответ усечён, пришёл отказ API или поток оборвался, не считать текст готовым и не запускать metadata-only восстановление.
- Если пришёл `end_turn` без ответа во всём текущем ходе после последнего учебного инструмента, вернуть скрытый `function_call_output` с причиной `answer_required`. Предыдущие аргументы отбросить; корректирующий раунд требует сначала пользовательский ответ, затем **новый** `end_turn`, чей саджест уже опирается на него. Forced tool choice не гарантирует наличие текста перед функцией, поэтому результат снова проверяется сервером. Если полноценный текст уже был в предыдущем раунде этого же хода, вызов без нового текста допустим для metadata-only восстановления; ответы прошлых ходов не подходят.
- Остальные невалидные вызовы получают скрытый `function_call_output` с конкретной причиной. Текст после вызова, повторный `end_turn` и смешанный пакет `end_turn` + учебный инструмент не считаются валидным завершением; метаданные не публикуются. После невалидного вызова нельзя применить его старый саджест к дописанному позже ответу.
- Максимум 6 раундов, 12 вызовов учебных инструментов и 60 секунд; завершение и исправление протокола входят в эти 6. При `parallel_tool_calls: false` фактически возможно до 5 учебных вызовов, если шестой занят завершением; 12 — дополнительный защитный потолок. Параллельные вызовы ради использования всех 12 — отдельное, пока не согласованное изменение.
- При недоступном резерве, stop или timeout новый принудительный запрос не запускать. Незавершённый протокол даёт `incomplete`, а не ложный `done`; уже полученный текст остаётся доступен.
- `end_turn` не расходует лимит поисковых/читающих действий и не создаёт UI step, но его токены и LLM-раунд полностью входят в стоимость и общий лимит раундов.

| Сценарий | Действие сервера | Если восстановление не удалось |
| --- | --- | --- |
| Готовый ответ, нет `end_turn` | Сохранить текст, один metadata-only раунд с forced `end_turn` | `incomplete`, текст доступен, прежнее название сохраняется, саджест отсутствует; не генерировать ответ заново автоматически |
| `end_turn` до ответа | Не применять аргументы; скрытая ошибка `answer_required`, один раунд «ответ → новый end_turn» | `incomplete`; пустой результат не выдавать за успешный ответ |
| Текст ответа был в предыдущем раунде этого хода, теперь только `end_turn` | Принять при валидных аргументах и завершённом потоке | При невалидных аргументах — общий ограниченный путь восстановления |
| Stop / timeout / EOF / усечение / нет резерва / исчерпаны 6 раундов | Новых запросов не запускать; сохранить полученный текст и учесть стоимость | Без частичных метаданных и без ложного `done` |

В обычном Responses API `required` требует инструмент, а forced function — конкретную функцию при успешном выполнении поддерживаемого запроса. Ответ без вызова при `auto` допустим; при `required`/forced это нарушение ожидаемого контракта либо незавершённый/ошибочный запрос, а не основание доверять одному HTTP 200. Порядок «ответ → вызов» всё равно проверяется приложением. Причины `missing_end_turn` / `answer_required` фиксировать в диагностике; не требовать от пользователя повторять весь вопрос ради метаданных.

### Саджест в интерфейсе

- Один саджест в placeholder пустого поля после успешного ответа. До принятия это не `draft`.
- Tab без модификаторов переносит текст в редактируемый черновик, но не отправляет его. Enter отправляет только настоящий черновик.
- Не перехватывать Shift+Tab, Tab без доступного саджеста, события IME или Tab при непустом поле.
- Саджест скрыт во время генерации, загрузки чата, при цитате и после ошибки/остановки.
- Новый вопрос, retry, переключение чата/аккаунта и изменение цитаты инвалидируют прежнее предложение. Устаревший callback не меняет состояние другого хода.
- Восстановление истории возвращает саджест последнего успешного ответа. После принятия скрываем его для текущего сообщения в открытой сессии, даже если черновик затем очищен.
- На touch показывать только placeholder. Кнопку «Вставить» и принятие касанием поля не добавлять. При `suggestion: null` виден существующий обычный placeholder; это подсказка интерфейса, а не реплика для вставки по Tab.

### Длинные чаты и сохранение контекста

- Согласовано: новые пределы истории — 15 сообщений или 50 000 символов; при достижении первого из них переводить **этот чат** на low, следующие ходы этого чата остаются low. Это ограничение стоимости, а не способ сохранить кэш при обрезке. Пользователь считает потери кэша на Luna приемлемыми.
- Под полем показывать: «Чат слишком длинный, качество снижено. Рекомендуем создать новый чат». Признак привязан к thread, восстанавливается после reload и не переносится через account-level degraded storage на другие чаты. Новый чат использует обычный выбор модели по квотам.
- Порог проверяется сервером до выбора модели, квоты и резерва нового run. Не выбирать high, а затем менять модель посреди запуска; low расходует low-квоту. При нехватке low-квоты обычная блокировка; молчаливого возврата в high нет. Повтор того же clientRequestId сохраняет исходный выбор.
- Предложенные ранее 96 000 символов / 64 сообщения снимаются: пользователь выбрал 15 / 50 000. **Рекомендация по поведению после предела:** оставить ограниченное скользящее окно на low, сохранять кэш в пределах окна и постоянных инструкций. Принудительное закрытие чата / обязательное создание нового не согласовано; предупреждение рекомендует новый чат. Само обрезание против закрытия на пределе ещё не считать разрешением менять продуктовый код.
- Reasoning и tool calls/results не удалять между ходами без необходимости. Для replay нужны целые сохранённые последовательности с matching tool outputs и сохранённым encrypted reasoning; нынешний `slice(-24)` может обрывать пары и не является готовым решением. 15 сообщений — логические user/assistant сообщения истории, не число reasoning/tool items. **Предложение учёта 50 000:** размер сериализованных items сохранённой истории, включая служебный контекст, tool calls/results и encrypted reasoning; это технический предел объёма, а не точное число токенов. Opaque reasoning не расшифровывать и не резать по символам: если блок не помещается, исключать целую старую последовательность. Новое сообщение и текущие инструментальные раунды по-прежнему имеют отдельные ограничения policy; не обещать, что maxHistoryChars — потолок всего upstream input. Кэш не заменяет передачу необходимого контекста.

Для сравнения цены ниже считаем **только повторный вход истории за один LLM-запрос**, условно 3 символа на токен. Это приближение для русского/формул, не результат токенизатора. Luna Standard: обычный input $0.10 / 1M, read $0.01 / 1M, 30m write $0.125 / 1M; цены проверены 24 ноября 2026.

| Переданная история | Приблизительно токенов | Обычный вход без cache hit | Если вся история записывается в 30m cache |
| --- | ---: | ---: | ---: |
| 24 000 символов | 8 000 | $0.0008 | $0.001 |
| 50 000 символов | ~16 667 | ~$0.001667 | ~$0.002083 |
| 240 000 символов | 80 000 | $0.008 | $0.01 |

Фактическая цена складывается из ordinary/read/write токенов. Дополнительно оплачиваются системный промпт, новые вопросы, tool outputs и output, включая reasoning; 1 000 output-токенов Luna — $0.0005. Если ход требует несколько запросов к модели, история оплачивается в каждом из них. Ни одну цену строки не выдавать за полную цену пользовательского ответа.

Предыдущие $0.08 / $0.51 — **сумма за 100 запросов**, не цена одного ответа. В условном примере на первом запросе передаётся 3k символов истории, на втором 6k, затем 9k и т.д. Без обрезки сумма — 3k × (1 + … + 100) = 15.15M символов; с окном 24k — 2.316M. При условных 3 символах/токен и обычной цене Luna это $0.505 / $0.0772. Здесь намеренно сравнивался только лимит символов, без нового ограничения 15 сообщений, cache hits, записи кэша, output и инструментальных раундов. Такой расчёт показывает накопление повторного входа, **но не доказывает, что обрезка дешевле сохранения кэшированного контекста**.

При идеальном повторном использовании префикса в том же примере 100k новых токенов оплачиваются как 30m writes ($0.0125), а 4.95M повторных — как reads ($0.0495): сумма $0.062, то есть ниже $0.0772 у маленького, но полностью некэшированного окна. Это иллюстрация при идеальных попаданиях, не прогноз hit rate. Для одного и того же повторяющегося префикса одна запись и одно полное чтение на Luna стоят 1.25 + 0.1 = 1.35 обычной цены вместо 2; одноразовые записи без повторного чтения, наоборот, дороже обычного входа.

Итого для выбора реализации: сохранять кэш и ограничивать историю совместимо. Пока префикс помещается в 15 / 50 000, его сохранять; при необходимости исключать целые старые блоки и принимать потерю части cache hits на low. Увеличивать контекст без предела ради процента cached tokens не нужно. Сравнивать общий расход, а не только hit rate. Перевод символов в токены в этих примерах относится к тексту; к длине encrypted reasoning это приближение неприменимо.

### Кэш: наблюдения и аудит текущего кода

Это prompt cache провайдера: повторное использование вычислений для совпадающего начала контекста, а не выдача старого готового ответа. [Парсер usage](../../../backend/src/responses-stream.ts) читает `cached_tokens` и `cache_write_tokens`, [расчёт цены](../../../backend/src/pricing.ts) раздельно учитывает обычный вход, чтение и запись кэша; [цикл](../../../backend/src/agent-loop.ts) суммирует их в `usage_runs`.

Read-only срез production D1 за скользящие 7 дней, полученный 24 ноября; активная версия всё ещё Codex, переключения на API не было:

| Модель | Запуски | Входные токены | Из кэша | Запуски с попаданиями |
| --- | ---: | ---: | ---: | ---: |
| Terra | 49 | 282 569 | 53 888 | 13 |
| Luna | 46 | 369 772 | 6 144 | 3 |
| Всего | 95 | 652 341 | 60 032 (9,2%) | 16 |

Во всех этих запусках `cache_write_tokens = 0`; 11 запусков имеют неопределённую стоимость из-за незавершённого обмена. Токены оборванного раунда могут отсутствовать в счётчиках: 9,2% — доля среди учтённых, не оценка всех запросов upstream. Скидка от **зарегистрированного чтения** относительно обычной цены тех же токенов по pricing version 1 — около $0,051747. Это уменьшение внутренней оценки расхода Codex, не подтверждённая экономия денег после перехода на API и не сравнение с ценой подписки.

В актуальном OpenAI API для Terra/Luna чтение дешевле обычного входа, но запись при default 30m стоит 1,25×. Поэтому на API нужно учитывать и cache reads, и cache writes: низкий hit rate сам по себе не гарантирует экономию. Нынешний parser/pricing умеет default 30m; 12h не включать без отдельной проверки тарифа и полей учёта. Поведение Codex OAuth и статистику его кэша нельзя автоматически переносить на API.

**Риски по коду; вклад каждого в фактический hit rate пока не измерен. Смену Terra → Luna риском не считаем:**

1. В [agent-loop](../../../backend/src/agent-loop.ts#L251) последний разрешённый раунд получает `tools: []`. Меняется ранняя часть контекста; будущий `end_turn` должен ограничиваться через tool choice при неизменном массиве определений. Это не требует отключать учебные функции удалением их схем.
2. [Инструкция первого названия](../../../backend/src/agent-loop.ts#L262) добавляется к `instructions`, а после получения названия исчезает. Префикс меняется уже между раундами первого хода. Удаление этого протокола в Task 4 устраняет причину; согласована единая nullable-схема с проверкой первого title в harness.
3. [buildSystemPrompt](../../../backend/src/tools.ts#L168) помещает текущую страницу, название документа и оглавление с «МЫ ЗДЕСЬ» в `instructions`. Навигация в том же чате или обновление каталога меняют префикс до истории. **Согласованное исправление:** стабильная базовая инструкция, актуальный контекст страницы / название чата — рядом с вопросом; прежние снимки не пересобирать.
4. [loadThreadHistoryInput](../../../backend/src/agent-loop.ts#L76) восстанавливает прошлые ходы из видимого текста: прежние tool calls/results и reasoning не возвращаются, а поисковая преамбула и ответ соединяются в одно сообщение. Это меняет сериализацию ранней истории относительно предыдущего запроса. Внутри текущего хода `outputItems` сохраняются. **Вариант оптимизации, пока не согласован:** replay сохранённых agent items с контролем объёма и совместимости; цена — больше входных токенов и сложнее обрезка. Не обещать, что хранение всей истории автоматически дешевле.
5. Тот же загрузчик ограничивает историю 16 сообщениями / 24 000 символами; при сдвиге окна изменяется начало переписки. Retry исключает заменяемые сообщения. Это необходимые ограничения и корректная семантика; улучшать кэш за счёт отмены лимита или возврата неверной истории нельзя.
6. [userTurn](../../../backend/src/agent-loop.ts#L157) добавляет страницу и дату вопроса. Дата стабильна при replay и между раундами одного хода, но различается между новыми вопросами. Для OpenAI API implicit breakpoint у последнего подходящего сообщения может не сохранить отдельно общий статический префикс. **Вариант для измерения:** reusable developer message с explicit breakpoint. Не удалять полезную дату из контекста и не считать это доказанным механизмом потерь у Codex OAuth.
7. В [usage_runs](../../../backend/migrations/0001_init.sql#L114) нет provider, а событие [codex_round](../../../backend/src/agent-loop.ts#L300) так называется для обоих провайдеров. После миграции нельзя смешивать старую и новую статистику и объявлять разницу экономией. Минимум — зафиксировать время переключения без активных старых запусков; для диагностики полезны provider, response ID, round usage и версия промпта без текста запросов/секретов.
8. [responses-stream](../../../backend/src/responses-stream.ts#L92) пересобирает assistant message, оставляя текст и теряя `phase` / ID. Это препятствие для точного replay и различения промежуточного / финального ответа; само отсутствие ID не доказывает cache miss. При реализации нового протокола сохранять поддерживаемую семантику output item и порядок, не приписывать потерю кэша полям без измерения.

Для названия согласована единая nullable-схема: стабильный tools-префикс, обязательность первого непустого названия — инструкция + серверная проверка. `first_title_required` входит в общий бюджет исправления протокола; после исчерпания раундов успешное завершение не подделывать.

Не считать самостоятельными проблемами `store: false`, случайный HTTP Idempotency-Key и отсутствие `prompt_cache_key` на этом поколении моделей. Время старого вопроса берётся из сохранённого `created_at`, а не обновляется на каждом раунде. Локальный кэш `AgentToolRunner` уменьшает повторные чтения D1 в пределах хода; это отдельный механизм, который не означает скидку на LLM input.

**Перед rollout:** измерить холодный и повторный API-запросы с одинаковым префиксом, затем многораундовый ход и следующий вопрос в том же чате. Сравнить общий расход с учётом write, read и output, отдельно долю cached input. Отсутствие hit расследовать по диагностике, а не превращать недетерминированный кэш в обязательное условие unit-теста. Оптимизации из этого аудита — варианты для отдельного согласования; сейчас меняется только план.

## Итоговые условия готовности

Перед исполнением завершить отдельный дизайн истории: выбрать окно либо полный replay до hard cap. Перевод длинного чата на low и неизменяемый контекст вопроса согласованы по поведению; для них нужен дополнительный этап ниже, без автоматического расширения rollout Tasks 1–6.

- Production напрямую использует OpenAI key из согласованного env-файла; повторный deploy сохраняет этот provider.
- D1 ограничивает новые запросы по учтённому расходу и резервам в рамках $15 / скользящие 7 дней, предупреждает на $12. Расход уже выполняющегося API-запроса окончательно известен после ответа; лимит не выдаётся за банковскую гарантию точного списания.
- Каждое успешное новое завершение имеет валидный скрытый `end_turn`; неуспешные завершения сохраняют текст без частичных метаданных.
- Первый успешный ответ даёт название, смена цели может изменить его, null оставляет прежнее.
- Саджест относится к завершённому ответу, не подменяет draft и вставляется без отправки.
- Полные backend/frontend проверки, браузерные сценарии и ревью пройдены. Перед PR дополнительно выполнить общие обязательные проверки из `context/process.md`; публикация — отдельное разрешённое действие.
